# ⚡ AI-Powered STA Debugger

**Parses raw Static Timing Analysis (STA) reports and uses an LLM to explain timing violations and suggest fixes — with admin-managed API access for shared use.**

---

## 🚀 Overview

Debugging Static Timing Analysis (STA) reports is one of the most time-consuming parts of chip design — engineers manually trace failing paths, slack values, and logic chains to figure out *why* a path violates timing and *how* to fix it.

**STA Debugger** automates the first pass of that work. It parses raw STA reports (from tools like OpenSTA or PrimeTime), extracts every timing path (startpoint, endpoint, slack, logic chain, pass/fail status), and sends each violated path to an LLM (via Groq) to generate a root-cause explanation, severity assessment, and prioritized fix suggestions — all through a Streamlit dashboard.

## ✨ Features

- **AI-Powered Analysis** — root cause, severity, and design-level fixes for each violated path, generated by Groq's `llama-3.3-70b-versatile`.
- **Custom STA Parser** — regex-based extraction of timing paths, slack, and logic chains from raw report text (no dependency on a specific EDA tool's export format).
- **Interactive Dashboard** — upload a report, configure analysis options, and review AI-generated results per path.
- **Report Export** — download results as JSON or PDF.
- **Admin-Managed API Access** — an admin provisions Groq API keys centrally; regular users pick from a dropdown of admin-provisioned keys instead of handling raw keys themselves.
- **Activity Logging** — every analysis run and login is logged per user, visible to admins in an activity log view.

## 🧠 How It Works

1. **Upload** — user uploads an STA timing report (`.txt`, `.rpt`, `.log`).
2. **Parse** — `STAParser` (`app/utils.py`) extracts startpoints, endpoints, logic chains, and slack for each path.
3. **Analyze** — parsed paths are sent to Groq's LLM (`app/inference.py`) for root-cause reasoning and fix suggestions.
4. **Review** — results render in an expandable Streamlit dashboard, one section per timing path.
5. **Export** — download the full analysis as JSON or PDF.

## ⚙️ Tech Stack

| Layer | Choice |
|---|---|
| UI | Streamlit |
| LLM | Groq (`llama-3.3-70b-versatile`) via LangChain |
| Parsing | Custom regex-based parser + Pydantic models |
| PDF export | ReportLab |
| Auth | Custom (JSON-file-backed, SHA-256 password hashing) |
| Storage | Flat JSON files under `models/` (no database) |

- `app/utils.py` — `STAParser` and PDF report generation.

## 🛠️ Installation & Setup

**Prerequisites:** Python 3.8+, a [Groq API key](https://console.groq.com/) (free tier available).

```bash
git clone https://github.com/<your-username>/STA-debugger.git
cd STA-debugger
pip install -r requirements.txt
streamlit run streamlit_app.py
```

No `.env` file is needed — API keys are entered through the app itself (see below), not read from the environment at startup.

## 📋 Using the App

1. **First run** — if no users exist yet, you'll be prompted to create the admin account.
2. **Admin: add an API key** — log in as admin → *Admin Panel → Manage API Keys* → add a Groq key with a label.
3. **Register a regular user** — from the login screen, click *Register*.
4. **User: run an analysis** — log in, pick an API key from the dropdown (never typed in directly by the user), upload a `.txt`/`.rpt`/`.log` report, click *Run Analysis*.
5. **Review & export** — inspect per-path results in the dashboard, download as JSON or PDF.
6. **Logs** — users see their own activity under *My Logs*; admins see everyone's under *View Activity Logs*.

## 🔒 Security Notes

This was built as a course/hackathon project, not a production system. Known tradeoffs, made consciously to keep scope reasonable:

- **API keys are stored in plaintext** in `models/api_keys.json` (gitignored, never committed) and only masked in the UI. A production version would encrypt these at rest.
- **Passwords are hashed with unsalted SHA-256**, not a slow, salted algorithm like bcrypt/argon2 — acceptable for a demo, not for real user data.
- **No database** — all state (users, keys, logs) lives in flat JSON files, which doesn't scale past a handful of concurrent users and has no transactional safety.
- **Sessions are in-memory** (Streamlit `session_state`) and don't survive a server restart.

These are documented here rather than fixed because reproducing production-grade auth/storage was out of scope for the project's goals — the interesting part is the parsing + LLM analysis pipeline.
